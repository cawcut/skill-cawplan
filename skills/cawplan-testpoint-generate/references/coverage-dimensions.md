# 覆盖维度参考清单（Coverage Dimensions）

> 本清单是测试点生成 Skill 的参考资产，落在 Skill 仓库 `references/coverage-dimensions.md`，随 Skill 分发、改动走版本控制。
> **用途**：为 obligation 的发现提供稳定知识，并统一测试点标签；具体五步流程只在 `SKILL.md` 定义。
> 本清单不落库、不进 CawPlan，也不是覆盖状态表。
> `obligation` / `disposition` / `basis` 术语定义见 `SKILL.md` §5；本文件只使用这些术语，不重新定义。

---

## 一、定位：发现知识，不是状态机

本清单包含路径类型、变化轴、关系分区和组合判据。它们只回答“还应发现哪些 obligation”，不各自维护覆盖 / 不适用 / 存疑状态，也不直接决定测试点行数。

- **变化轴**：提示输入、状态、角色、并发等可能改变行为的方面。
- **路径类型**：提示正常、非法、临界、反向等基本方向，也可作为主标签。
- **关系分区**：提示比较、状态、依赖、归属及前后变化是否覆盖完整。
- **组合判据**：只展开可能改变行为的因素组合，禁止无意义全量笛卡尔积。

> **原则**：每次发现都进入 `SKILL.md` 定义的同一 obligation 清单；本文件不要求输出逐轴判断、逐项勾选或独立分区表。

---

## 二、使用纪律

1. **相关性优先**：只发现与功能形态相关的方向；A/B 轴明确不涉及时可不产生 obligation。
2. **C/D 不对称兜底**：八个 C/D 轴只有下表正面证明不适用时才可排除；否则必须产生测试点或存疑 obligation。
3. **先分开、后合并**：可能导致不同结果的值、状态、关系或组合先分别发现；是否合并留到 `SKILL.md` Step 4。
4. **不把知识变成账本**：不得输出覆盖矩阵、逐轴状态、清单勾选或“已全部覆盖”的声明。
5. **红线不变**：本清单只能补充方向，不提供未写明的数值、阈值、文案、错误码、隐藏规则或具体实现。

### 二.1 · C/D 八轴正面证明可静默（形态门槛表）

> **用途**：C/D 轴仅当五字段形态**正面证明**不适用时，才允许静默跳过。凡需「论证该功能有没有副作用 / 持久化 / 多角色」才能得出不适用的，**一律不得静默**，改走存疑兜底。
>
> **凡需要论证才能排除的，不得静默** — 下表左列是「五字段已呈现的形态」；右列是**在该形态下可静默的 C/D 轴**（未列出者默认存疑）。

| 五字段正面形态（须已写明或可直读，非推断） | 可静默的 C/D 轴 |
|---|---|
| 纯只读 / 纯展示，无任何写入·扣减·状态变更 | `幂等`、`并发`、`一致性` |
| 无共享资源·无限量计数（且形态上无写入扣减） | `并发` |
| 纯后端内部，五字段无多端·多客户端·网络依赖线索 | `环境兼容` |
| 全新独立功能，不改存量数据 / schema / 老流程 | `存量兼容` |
| 无个人 / 支付 / 敏感操作 | `安全审计` |
| 非关键链路，五字段无任何高峰 / 容量 / 响应 / 大数据量线索 | `性能` |
| 纯静态展示，五字段无失败定位 / 日志 / 告警 / 监控线索 | `可观测` |

> 同一需求可同时命中多行；某轴仅当**至少一行**将其列入右列，且五字段形态满足该行左列时，方可静默。命中左列形态但右列未列出该轴 → 仍进存疑。

## 三、路径类型 / 取值类

以下四词既用于发现基本盘 obligation，也用于标注覆盖标签；它们不是待维护的独立轴状态。

| 标签词 | 含义 | 适用判断 |
|---|---|---|
| `正向` | 正常输入、正常路径下功能是否达到预期 | 恒适用；每个功能均应有正向 obligation |
| `边界` | 在某根轴上取**合法范围内的临界值**（上下限、最大最小、恰好卡点） | 凡输入 / 数量 / 长度 / 时间存在范围即适用 |
| `异常` | 明确**非法、缺失、损坏**的输入是否被正确拦截、提示是否清晰 | 凡接受外部输入即适用 |
| `逆向` | 取消、撤销、回退等**反向操作**是否正确 | **仅当**功能含可取消 / 可撤销动作时适用；一次性无状态操作不适用 |

> **基本盘 `异常` 与需求未写明**：需求未单独写失败场景时，若本节判 `异常` 适用，仍应形成 obligation，并按 `SKILL.md` Step 3 生成方向性测试点（应拦截 / 应失败 / 应有明确提示）或存疑；具体文案、次数、错误码不得编造。

> **`边界` 与 `异常` 的分工**：`边界` 指合法范围内的极限值（如字段长度恰好等于上限时仍能正常提交）；`异常` 指明确非法或损坏（如提交空值、超出上限、格式错误）。前者"极限但合法"，后者"直接非法"。
> **`边界`/`异常` 不限于输入类型**：任意**带范围的变化轴**都可取这两类值——数量有上限、时间有超时、并发有峰值。取边界值时勿只想输入长度，也要想超时、峰值、计数上限等。
> **`逆向` 不列入高频必测的原因**：其对一次性无状态操作（如单次查询、单次计算）无意义，强套将导致过度生成。仅在存在"取消 / 撤销 / 回退"动作时测。
> **`逆向` 的取值追问**：撤销 / 重做 / 重试的**作用范围**是"整体回退"还是"仅回退当前对象 / 当前步骤"？多步操作中途撤销，前面已完成的步骤是否受影响？作用范围需求未写清时，标 `待确认` 进存疑。

## 四、变化轴（用于发现 obligation）

列含义：**轴名（标签词）** | **本轴考察什么** | **发现时的展开追问（方向提示）** | **适用判断 + 与相邻轴的分工**。
示例取自不同业务场景（表单提交 / 账号登录 / 订单支付 / 数据同步），以提示 AI 勿仅套用单一场景。

### A 组 · 输入、界面与结果主路径类（高频适用）

| 轴名（标签词） | 本轴考察什么 | 发现时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `输入类型` | 输入的种类 / 形态发生变化时是否均正确 | 空值 / 缺失必填项？超长 / 超大内容？特殊字符 / 编码 / 乱码？多项 / 批量提交？**单个操作与批量操作行为是否一致、两者混用时**是否需专门交叉验证？不同格式或类型？取到上下限 / 临界值（配 `边界` 标签）？非法 / 损坏输入（配 `异常` 标签）？ | 凡有用户输入即适用。**分工**：`输入类型` 回答"哪种输入在变"；以 `正向 / 边界 / 异常` 标注该条取的是正常值 / 临界值 / 非法值。示例：表单—必填留空 / 超长文本 / 含脚本字符；登录—错误账号/密码（`异常`）；用户名含空格 / 密码超长（`异常`）；支付—金额为 0 / 负数 / 超大额；列表—单选操作 vs 批量选中操作。 |
| `交互反馈` | 操作过程中界面的**反馈与可交互状态**是否正确、可感知 | 触发后是否有进行中 / 加载态、完成前是否禁止重复触发？成功 / 失败是否有明确反馈（toast / 跳转 / inline 提示——标注**类型**而非文案）？达上限 / 不可用 / 无权限时入口是否置灰或拦截并给方向性提示？无数据时是否有空态？破坏性 / 不可逆操作前是否二次确认？长耗时操作有无进度或可感知反馈？ | 凡有用户界面即适用（高频，同 `输入类型`）；纯后端 / 无界面不适用。**分工**：输入值本身的合法性归 `输入类型`；对象状态机流转归 `状态迁移`；后端重复执行的副作用归 `幂等`；本轴只覆盖"UI 层对状态 / 结果的反馈与可交互性"这一层。示例：删除前二次确认；列表无数据显示空态；提交进行中按钮置灰且显示进行中态。 |
| `结果有效性` | 功能产生最终结果 / 产物时，结果本身是否**准确、完整、符合要求且可正常消费 / 使用**，而不只验证是否成功产生 | 最终结果是否真正实现需求 / 用户明确要求的核心目标，关键要求是否正确体现在最终产物中？**凡会影响最终产物的输入、配置或参数，是否真实、正确地作用并体现在最终结果中，而不只验证参数已选择、保存或界面已更新？**产物内容、数据、对象或关联关系是否正确，有无错误、错配或遗漏？应包含的内容是否完整，有无截断？格式、结构、类型是否符合需求并可解析？是否可正常查看、打开、播放、下载、发送、导入或继续使用？多份 / 多对象产出时，是否与对应输入、对象正确关联？ | 功能会产生供用户消费或后续使用的最终结果 / 产物时适用，包括图片、视频、文件、Email、AI 生成的测试点 / 用例、Agent 对话 / 引导或执行结果。**分工**：`交互反馈` 只验证界面是否正确反馈结果；`结果有效性` 验证产物本身是否有效；写入后的持久化 / 跨服务读取归 `一致性`；AI 特有的指令遵循、事实依据等仍应由相应专项维度发现。需求未定义的主观品质标准（如“好看”“专业”）不得自行补充。示例：导出的 CSV 字段和值完整正确且可正常打开；生成的视频与输入要求对应、完整可播放；发送的 Email 收件人、主题、正文、附件与要求一致。 |

> **`交互反馈` 轴上的测点，主标签取 `交互反馈`**；是否属于正常 / 临界 / 异常反馈，写在标题方向里，**勿用路径类型替代主标签**。

### B 组 · 状态与角色类（涉及状态流转或多角色时适用）

| 轴名（标签词） | 本轴考察什么 | 发现时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `状态迁移` | 业务对象的状态机是否闭环，有无孤儿状态 / 非法迁移 / 超时流转 | 有哪些状态？哪些迁移合法、哪些应被拦截？失败可否重试？超时是否自动流转？是否存在无法退出的死状态？有没有"未设置 / 已设默认值 / 已设自定义值"这类**配置前置态**，各态下表现是否不同？"编辑中（未保存）"与"确认 / 保存后"是否分开？编辑/更新时还要检查**不改直接保存、只改部分字段且其余字段保持不变**。 | 对象存在多个状态或可编辑持久状态时适用；无状态的纯计算 / 纯展示不适用。**分工**：`状态迁移` 关注对象状态如何流转；"处理中点击取消"归 `逆向`；"保存后重开数据是否还在"归 `一致性`。 |
| `角色权限` | 不同角色 / 等级 / 登录态的**可见范围与操作边界**是否正确；以及能否**越界**访问不属于自己的数据 | 不同等级 / 登录与未登录 / 管理员与普通用户的差异是否生效？修改 ID 能否访问他人数据？普通用户能否执行管理员操作？跨租户是否隔离？授权能否继续传递且不超过授权者？降权/撤销是否及时生效？绕过前端直接调用后端是否仍被拦截？ | 存在多角色 / 等级 / 私有数据时适用；全员一致且无私有数据则不适用。**分工**：合法身份能力差异、权限传递/撤销和后端越权均归本轴，不另建重复轴。 |
| `来源入口` | 同一功能从不同入口 / 来源触发时表现是否一致 | 存在几个入口？从不同页面、外部链接、API 分别触发，行为是否一致？ | 功能有多个触发入口时适用；单一入口不适用。示例：从列表页、详情页、通知跳转三处发起同一操作，结果是否一致。 |

### C 组 · 并发与数据类（涉及写入、扣减，或数据存于多处时适用）

| 轴名（标签词） | 本轴考察什么 | 发现时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `幂等` | **同一操作重复执行**（连点 / 重试 / 重复消息）结果是否与执行一次相同 | 连续点击提交是否重复扣款 / 重复创建？超时重试是否执行两次？重复回调 / 重复消息如何处理？ | 凡有"提交 / 扣减 / 写入"即适用；纯读取 / 纯前端计算不适用。**分工**：`幂等` 为同一操作**重复多次**；`并发` 为多操作**同时**作用于同一资源。示例：连续点击三次提交，是否仅扣款一次、仅创建一笔订单。 |
| `并发` | 同一资源被**同时多次**操作时是否正确、无竞态 | 同一账号同时发起多个请求会怎样？限量 / 限流 / 计数在并发下是否准确？是否会超卖 / 超发？ | 存在共享资源 / 限量 / 计数时适用；无共享状态不适用。**分工**：与 `幂等` 的区别在"同时"与"重复"。示例：同一账号并发提交多笔下单，库存扣减与限流是否正确。 |
| `一致性` | 数据存于多处（主从库 / 缓存）或先写后读时，读到的是否正确且最新 | 写入后立即读取是否可读到（主从延迟）？缓存是否返回旧值？跨表 / 跨服务数据是否一致？**保存后退出重进 / 重新打开 / 重新登录，数据是否仍在且一致**（持久化验证，区别于编辑中的临时态——后者归 `状态迁移`）？ | 存在跨库读写 / 缓存 / 写后立即展示 / 需持久保存时适用；纯单点无持久化不适用。示例：提交订单后跳转"我的订单"新订单是否立即出现；设置项保存后退出重进是否保留。 |

### D 组 · 变更与非功能类（改动存量，或线上关键链路时适用）

| 轴名（标签词） | 本轴考察什么 | 发现时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `存量兼容` | 升级 / 加字段 / 改逻辑后，**老数据、老流程**是否仍正常、能否回滚 | 新增必填字段后老数据能否正常读取？逻辑变更后旧记录是否仍正确？可否回滚？数据迁移中断如何处理？老数据/老结构进入新逻辑后，与其配套的其它状态（计数、顺序、下游引用、持久化结果）是否也随之正确联动，而不仅是"能打开/未报错"？ | 改动已有功能 / 数据结构时适用；全新独立功能不适用。**分工**：`存量兼容` 仅涉及**数据 / 版本 / schema** 的向后兼容，**不含运行环境兼容**（后者归 `环境兼容`）。示例：为订单表新增必填字段后，历史订单打开是否报错、能否回滚。 |
| `环境兼容` | 不同**运行环境 / 客户端 / 网络**下是否均正常 | 不同浏览器 / 分辨率？旧版本 App / 旧客户端是否仍可用？弱网 / 断网 / 超时如何表现？中断后能否重试或恢复？ | 存在多端 / 多客户端 / 明显网络依赖时适用；纯后端内部功能可不适用。**分工**：`环境兼容` 关注运行环境与网络（设备 / 浏览器 / 弱网）；`存量兼容` 关注数据 / 版本升级。二者常被混淆，须区分。示例：旧版本客户端打开新功能是否正常降级；弱网下请求超时后能否重试。 |
| `性能` | 高频 / 高峰 / 大数据量下的响应与容量边界 | 高峰并发下响应时间是否达标？大数据量下是否拖垮？排队时长是否可接受？ | 关键高频链路、有明确性能要求时适用；低频内部功能可不适用。示例：高峰期批量请求下的响应时长与成功率是否达标。 |
| `安全审计` | 敏感数据是否脱敏、敏感操作是否留痕可审计 | 手机号 / 支付信息展示是否脱敏？敏感操作是否有日志可查？数据落库是明文还是加密？ | 涉及个人信息 / 支付 / 敏感操作时适用；无敏感数据不适用。**分工**：`安全审计` 关注"应隐藏的是否隐藏、应留痕的是否留痕"；`可观测` 关注"出问题能否定位"。示例：操作记录中手机号是否脱敏、不落明文。 |
| `可观测` | 关键路径是否有日志 / 追踪 ID / 告警 / 监控，出问题能否定位 | 失败能否查到卡在哪一步？是否有追踪 ID 串联全链路？失败率是否有监控告警？ | 线上关键链路适用，越核心越应覆盖；纯静态展示可不适用。示例：请求失败能否定位失败环节、当日失败率是否有告警。 |

### E 组 · AI / Agent 行为类（AI / Agent 形态按需启用）

> **启用条件**：当五字段或功能形态能够确认该功能的核心结果或行为由 **AI / 模型能力**产生，或涉及 **Agent / Tool Calling 的自主决策与执行**时，启用本组；**不要求需求中显式出现 “AI / Agent / LLM” 等字样**。
>
> 判断应以功能语义和能力形态为准。例如，需求明确呈现 **Prompt / 自然语言指令 + Model / 生成模型 + 文本、图片、视频等生成结果**，或具有 AI 问答、总结、分类、提取、多轮对话等模型处理形态时，均可视为 AI 能力；涉及 Agent 根据目标自主选择、编排或调用工具执行任务时，视为 Agent / Tool Calling 能力。单独出现 `Prompt`、`Model` 等词不足以判定，应结合其在功能中的实际作用判断。
>
> 普通确定性功能不启用本组。启用 E 组后，**仅按各轴自身的适用条件发现 obligation**，不要求所有 E 轴都产生测试点，也不采用 C/D 组的强制存疑兜底；明确不涉及的轴可直接跳过，避免因“属于 AI / Agent”而机械产生无意义测试点或存疑。
>
> **非确定性结果判定**：AI 输出不要求逐字一致，重点验证关键语义、结论、约束和不变量是否保持正确、稳定；需求未定义的通过率、评分、阈值或标准答案不得自行补充。

| 轴名（标签词） | 本轴考察什么 | 发现时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `指令遵循` | AI 是否正确理解并遵循用户 / 系统明确给出的要求与约束 | 明确要求是否全部执行？数量、语言、格式、范围等约束是否遵守？“不要 / 禁止 / 仅”等否定或限定要求是否生效？多条要求同时存在时是否遗漏其中一条？后续要求修改前文要求时，是否按最新有效要求执行？存在冲突指令时是否按已定义的优先关系处理，而非自行选择？ | 凡结果依赖模型理解并执行自然语言指令时适用。**分工**：`输入类型` 关注输入本身发生变化；`结果有效性` 关注最终产物是否实现目标、准确完整可用；本轴专门关注“明确给出的指令有没有被遵守”，不重复验证产物本身。 |
| `事实依据` | AI 输出中的事实、数据、引用、规则或结论是否具有可用依据，避免无依据生成或擅自补全 | 输出是否忠于提供的 Requirement、文档、检索结果或其他已知来源？是否出现来源中不存在的事实、数字、引用、规则或状态？资料不足时是否明确保留不确定性 / 请求补充，而不是自行补全？多个来源存在差异时是否避免无依据地合并成确定结论？ | 当 AI 输出依赖 Requirement、文档、知识库、检索结果、外部数据等事实来源时适用；纯创意生成可不适用。**分工**：`结果有效性` 判断最终结果是否正确完整；本轴进一步检查“这些内容是否有依据、有没有编造”。需求本身未提供的规则仍受本清单红线约束，不得自行推断。 |
| `输出稳定性` | AI 非确定性输出在重复或等价输入下，关键语义、结论、约束和不变量是否保持稳定 | 相同输入重复执行时，关键结果是否出现明显漂移或偶发严重错误？同义改写、顺序调整等不改变原意的输入是否导致关键结论改变？明确要求的格式、分类、关键业务规则等是否能够稳定保持？模型 / Prompt 等发生变更后，已有关键场景是否出现结果退化？ | AI 输出具有非确定性，且关键结果需要保持稳定时适用。**不要求逐字一致**，只比较会影响业务正确性的关键语义、结论、约束和不变量。**分工**：`幂等` 关注重复执行是否产生重复业务副作用；本轴关注重复生成时 AI 结果质量是否出现不可接受的漂移。具体次数、通过率或允许波动范围未定义时不得自行编造。 |
| `上下文` | AI 是否正确使用当前任务需要的上下文，并避免遗漏、误用或串用不属于当前任务的信息 | 多轮对话中前文关键条件是否继续生效？“它 / 上一个 / 刚才那条”等指代是否正确关联？用户后续修改要求后，旧要求是否被正确更新而非继续错误沿用？长上下文中关键约束是否被遗漏？不同任务、会话、用户或对象之间的信息是否错误串用？ | 存在多轮对话、上下文引用、历史信息或记忆能力时适用；单轮且输入已自包含的生成任务可不适用。**分工**：`指令遵循` 判断已经识别出的要求是否被执行；本轴关注“该使用哪些上下文、是否正确继承 / 更新 / 隔离”。 |
| `Agent 执行` | Agent / Tool Calling 是否选择并正确执行完成任务所需的动作，同时将真实副作用控制在用户意图和授权范围内 | 是否选择正确工具并提供正确参数？缺少关键参数时是否先澄清而非臆造？多步任务是否按依赖顺序执行，有无遗漏或无意义调用？工具失败、超时、空返回时是否正确停止、重试、恢复或如实反馈，而不是带错继续？是否出现重复调用、无效循环或无法终止？执行后是否验证真实结果，而不是仅凭工具调用成功就宣称任务完成？涉及发送、删除、修改、发布等真实副作用时，执行对象、范围和动作是否符合用户明确意图及授权？ | **仅 Agent / Tool Calling / 代执行类功能适用**；纯文本、图片等内容生成不适用。**分工**：工具调用产生的普通重复写入仍归 `幂等`，角色 / 数据访问边界仍归 `角色权限`，敏感数据与审计仍归 `安全审计`；本轴关注 Agent 自主选择、编排和执行动作本身是否正确，以及真实动作是否超出用户意图。 |

## 五、关系分区知识

仅当需求或功能形态存在对应关系时使用；每个分区先形成独立 obligation，具体预期未知时交给存疑，不得猜。

| 关系类型 | 触发形态 | 优先检查的完整分区 |
|---|---|---|
| 比较关系 | 两个数量、版本、优先级或时间点相比较 | `< / = / >`；若语义是包含边界，再区分边界内 / 恰好边界 / 边界外；配置、容量或上限发生切换时，按新值相对旧值分别检查变小 / 相等 / 变大 |
| 数量关系 | 有空集、单项、多项、容量或配额 | `0 / 1 / 多个`；有上限时检查低于 / 等于 / 高于上限 |
| 位置关系 | 对有顺序的集合删除、插入、替换或重排某项 | 首位 / 中间 / 末位；仅当单项集合会产生不同结果时补唯一项 |
| 状态关系 | 对象存在状态机或前置状态 | 合法迁移 / 非法迁移；动作前 / 处理中 / 动作后；失败后的重试或恢复 |
| 依赖关系 | 结果依赖服务、资源、授权或网络 | 依赖可用 / 不可用 / 恢复后；仅在确有依赖时展开 |
| 归属关系 | 存在所有者、协作者、租户或私有数据 | 本人 / 他人 / 跨租户；仅展开功能实际存在的层级 |
| 变化关系 | 需求修改既有行为或声明不变量 | 变更前 / 变更后 / 重开或重进；受影响对象 / 明确不受影响对象 |

## 六、有意义组合知识

两个因素组合后，若可能改变**可用性、结果、状态、副作用、反馈、影响范围或恢复行为**，发现对应组合 obligation；否则不组合。

- 默认检查二元组合，不做全量笛卡尔积。
- 三元组合仅在需求明确三因素联动，或任何二元组合都无法表达风险时发现。
- “同一目标只有测试数据不同”不是新组合目标，留到 Step 4 合并；角色、套餐、状态等额外前置改变行为时则应分开。
- 不确定是否改变行为时保留组合 obligation，交 Step 3 分流；不得凭“可能太多”提前删除。

## 七、标签标注规则

**跟随会话语言**：英文会话下，`tags` 用 `references/terminology-en.md` 第 5 节的英文词（如 `角色权限` → `Role & Permission`、`正向` → `Positive`），本节判断依据（哪个场景取哪个标签）不变，只是落地时换成对应英文词；已冻结，**不要**临时现场翻译出与该表不同的说法，也不要同一 Requirement 下中英文标签混用。**该规则同样适用于下方「补充标签」与「表外词」**：英文会话下这两类自造词也须译成英文，**不得**照抄本清单里的中文示例措辞（如下方 `SSO超时`、`弱网` 只是中文场景下的示例，英文会话下对应写 `SSO Timeout`、`Weak Network` 或同义英文表达，不是逐字搬运）；若同 Requirement / 同产品下已有既有英文测试点用词，优先复用其英文表达以收敛同义词。

**主标签位置与标准词契约（硬性）**：`tags[0]` 是一条测试点的唯一主标签，必须严格使用本文件路径类型或变化轴中的标准词；英文会话必须使用 `references/terminology-en.md` 中对应的正式英文词。补充标签只能放在 `tags[1]`。不得把表外词、同义词或具体场景词放在 `tags[0]`。

- **一条测试点主要标注 1 个标签**（主标签，固定放在 `tags[0]`）：优先取**最具体、信息量最高**的变化轴（如涉越权场景取 `角色权限`）；若没有更具体的变化轴，该条属普通正常 / 临界 / 非法检查，则取路径类型词（`正向 / 边界 / 异常`）。
- **必要时至多再加 1 个补充标签**（固定放在 `tags[1]`；具体场景词，如 `SSO超时`、`弱网`），便于人工扫视定位。**禁止单条测试点标注过多标签**，以免污染看板统计。
- 补充标签确需使用表外词时，先参考同 Requirement / 同产品既有测试点的用词，尽量复用，以收敛同义词。

## 八、备注与边界

- **A/B/C/D/E 仅为发现顺序与形态分组**：A 组高频适用，B/C/D 按功能形态启用；E 组仅在五字段或功能形态明确包含 AI 生成、模型输出、多轮 AI、Agent 或 Tool Calling 时启用。A/B/E 组各轴明确不涉及时可不产生 obligation；C/D 八轴默认进入测试点或存疑，除非 §二.1 正面证明不适用。
- **C、D 组最易遗漏，也最易被误判为不适用**：只有 §二.1 的正面形态门槛可以排除，不得用“需求未提”静默略过。E 组不套用该强制兜底规则，启用后仍按每根轴自己的适用条件发现 obligation，避免因为“属于 AI / Agent”而机械产生无意义测试点或存疑。
- **标签非覆盖账本**：补充标签仍为自由文本，且变化轴可能因判不适用而静默，**看板的"标签分布"仅为尽力而为的参考，非权威覆盖记录**。覆盖完整性以人工 review 测试点为准，而非统计标签数量。
- **表外维度允许、按产品可扩**：若产品重度涉及**国际化 / 时区 / 多语言**，或 SQA 范围包含**可用性**等，可按需在变化轴层补轴（先复用已有补充标签，确无再新增）。本版暂不含上述维度；表外维度词只能作为 `tags[1]` 的补充标签，未纳入标准词表前不得放入 `tags[0]`。
- **文件命名**：进仓库使用英文名 `references/coverage-dimensions.md`（校验仅要求路径可解析，中文正文不受影响）。
