# 覆盖维度参考清单（Coverage Dimensions）

> 本清单是测试点生成 Skill 的参考资产，落在 Skill 仓库 `references/coverage-dimensions.md`，随 Skill 分发、改动走版本控制。
> **用途**：测试点生成时对照本清单枚举覆盖面以防漏；贴覆盖标签时统一用词；交稿自查时作为反查基准。
> 本清单不落库、不进 CawPlan，仅作为生成时的参照与标签取值来源。

---

## 一、两类词的区分：变化轴与路径类型

本清单包含两类性质不同、用法不同的词，须先区分：

- **变化轴**：描述一个功能"**哪个方面可以发生变化**"——输入形态、对象状态、操作角色、并发情形等。AI 以变化轴为单位枚举，并在轴上取值**叉乘**生成测试点（例如「超长文本」×「长度上限」得到一条测试点）。变化轴是本清单主体，见第四节。
- **路径类型 / 取值类**：描述一条测试点属于"**哪一种检查**"——正常路径、非法输入、临界取值、反向操作。它们**不参与叉乘**，仅用于为测试点标注覆盖标签。共四个词，见第三节。

> **原则**：AI 仅在"变化轴"上枚举与叉乘，**不得将 `正向` 等路径类型当作变化轴参与叉乘**——否则会产出大量重复的正向测试点，并使看板中 `正向` 标签占比虚高、丧失诊断价值。

---

## 二、使用定位与三条纪律

本清单在测试点生成的三处被引用，且三处**使用同一套词**（收敛用词，使看板标签分布可解释）：枚举取值时（对照变化轴想全该测的面）、标注标签时（覆盖标签优先取本清单词）、交稿查漏时（对照清单找疑似遗漏的轴）。

> **具体生成流程、数量把控、端到端示例见 SKILL.md，本清单不重复。** 本清单只提供"有哪些轴、各是什么、如何区分、标签怎么取"这些稳定知识。

**三条使用纪律：**

1. **软推荐，不锁枚举**：本清单是建议标签时的首选词库；人可增改、可用表外词。目的是收敛用词，而非限制表达。
2. **按相关性选用，A/B 与 C/D 三态纪律不同**：
   - **A/B 组变化轴**：不要求每个功能覆盖所有轴。判定为**明确不适用**的轴 → **静默跳过**（不生成、不汇报）；判定**不确定**的轴 → 写入**存疑清单**交人确认。
   - **C/D 八轴**（`幂等` / `并发` / `一致性` / `存量兼容` / `环境兼容` / `性能` / `安全审计` / `可观测`）：**默认存疑兜底** — 仅当五字段能**正面证明**不适用（见 §二.1 形态门槛表）→ 静默跳过；否则即便倾向判不适用，也须在存疑清单留一行：`〔X 轴〕判为本次不测（原因：…）/ 是否需覆盖，请确认`（方向性表述，不编造具体值，不因此生成测点）。多轴同一缺口合并一行。
   - 基本盘路径类型（第三节 `正向` / `异常` / `边界`）判适用时，优先生成**方向性**代表测点；拿不准**实现方式或范围**时进存疑（见 SKILL.md 红线 0）。路径类型三态逻辑不变。
3. **自查用于暴露疑点，而非逐项勾选（红线）**：
   - 存疑清单仅记录：疑似遗漏的轴 + 原因 + 建议动作。
   - 已覆盖的轴：默认不汇报。
   - **A/B 轴**：判定明确不适用者静默；判定不确定者方在存疑清单中点明。
   - **C/D 八轴**：未正面证明不适用者默认进存疑（格式见上）；仅 §二.1 形态门槛可证不适用者静默。
   - **不得输出 `☑正向 ☑边界 ☑异常` 形式的完整勾选表**——勾选表会制造"已全部覆盖"的假象，反使清单未列的盲区无人排查。

### 二.1 · C/D 八轴正面证明可静默（形态门槛表）

> **用途**：C/D 轴仅当五字段形态**正面证明**不适用时，才允许静默跳过。凡需「论证该功能有没有副作用 / 持久化 / 多角色」才能得出不适用的，**一律不得静默**，改走存疑兜底。
>
> **凡需要论证才能排除的，不得静默** — 下表左列是「五字段已呈现的形态」；右列是**在该形态下可静默的 C/D 轴**（未列出者默认存疑）。

| 五字段正面形态（须已写明或可直读，非推断） | 可静默的 C/D 轴 |
|---|---|
| 纯只读 / 纯展示，无任何写入·扣减·状态变更 | `幂等`、`并发`、`一致性` |
| 无共享资源·无限量计数（且形态上无写入扣减） | `并发` |
| 纯后端内部，五字段无多端·多客户端·网络依赖线索 | `环境兼容` |
| 全新独立功能，不改存量数据 / schema / 老流程 | `存量兼容` |
| 无个人 / 支付 / 敏感操作 | `安全审计` |
| 非关键链路，五字段无任何高峰 / 容量 / 响应 / 大数据量线索 | `性能` |
| 纯静态展示，五字段无失败定位 / 日志 / 告警 / 监控线索 | `可观测` |

> 同一需求可同时命中多行；某轴仅当**至少一行**将其列入右列，且五字段形态满足该行左列时，方可静默。命中左列形态但右列未列出该轴 → 仍进存疑。

## 三、路径类型 / 取值类（仅标注，不叉乘）

以下四词描述一条测试点属于"哪一种检查"，**不参与叉乘**，仅用于标注覆盖标签。

| 标签词 | 含义 | 适用判断 |
|---|---|---|
| `正向` | 正常输入、正常路径下功能是否达到预期 | 恒适用；每个功能均应有正向测试点 |
| `边界` | 在某根轴上取**合法范围内的临界值**（上下限、最大最小、恰好卡点） | 凡输入 / 数量 / 长度 / 时间存在范围即适用 |
| `异常` | 明确**非法、缺失、损坏**的输入是否被正确拦截、提示是否清晰 | 凡接受外部输入即适用 |

> **基本盘 `异常` 与需求未写明**：需求未单独写失败场景时，若本节判 `异常` 适用，仍应生成**方向性**代表测点（应拦截 / 应失败 / 应有明确提示）；具体文案、次数、错误码不得编造 — 见 SKILL.md **红线 0**。
| `逆向` | 取消、撤销、回退等**反向操作**是否正确 | **仅当**功能含可取消 / 可撤销动作时适用；一次性无状态操作不适用 |

> **`边界` 与 `异常` 的分工**：`边界` 指合法范围内的极限值（如字段长度恰好等于上限时仍能正常提交）；`异常` 指明确非法或损坏（如提交空值、超出上限、格式错误）。前者"极限但合法"，后者"直接非法"。
> **`边界`/`异常` 不限于输入类型**：任意**带范围的变化轴**都可取这两类值——数量有上限、时间有超时、并发有峰值。取边界值时勿只想输入长度，也要想超时、峰值、计数上限等。
> **`逆向` 不列入高频必测的原因**：其对一次性无状态操作（如单次查询、单次计算）无意义，强套将导致过度生成。仅在存在"取消 / 撤销 / 回退"动作时测。
> **`逆向` 的取值追问**：撤销 / 重做 / 重试的**作用范围**是"整体回退"还是"仅回退当前对象 / 当前步骤"？多步操作中途撤销，前面已完成的步骤是否受影响？作用范围需求未写清时，标 `待确认` 进存疑。

## 四、变化轴（用于枚举与叉乘）

列含义：**轴名（标签词）** | **本轴考察什么** | **生成时的展开追问（取值提示）** | **适用判断 + 与相邻轴的分工**。
示例取自不同业务场景（表单提交 / 账号登录 / 订单支付 / 数据同步），以提示 AI 勿仅套用单一场景。

### A 组 · 输入与主路径类（高频适用）

| 轴名（标签词） | 本轴考察什么 | 生成时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `输入类型` | 输入的种类 / 形态发生变化时是否均正确 | 空值 / 缺失必填项？超长 / 超大内容？特殊字符 / 编码 / 乱码？多项 / 批量提交？**单个操作与批量操作行为是否一致、两者混用时**是否需专门交叉验证？不同格式或类型？取到上下限 / 临界值（配 `边界` 标签）？非法 / 损坏输入（配 `异常` 标签）？ | 凡有用户输入即适用。**分工**：`输入类型` 回答"哪种输入在变"；以 `正向 / 边界 / 异常` 标注该条取的是正常值 / 临界值 / 非法值。示例：表单—必填留空 / 超长文本 / 含脚本字符；登录—错误账号/密码（`异常`）；用户名含空格 / 密码超长（`异常`）；支付—金额为 0 / 负数 / 超大额；列表—单选操作 vs 批量选中操作。 |

### B 组 · 状态与角色类（涉及状态流转或多角色时适用）

| 轴名（标签词） | 本轴考察什么 | 生成时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `状态迁移` | 业务对象的状态机是否闭环，有无孤儿状态 / 非法迁移 / 超时流转 | 有哪些状态？哪些迁移合法、哪些应被拦截？失败可否重试？超时是否自动流转？是否存在无法退出的死状态？有没有"未设置 / 已设默认值 / 已设自定义值"这类**配置前置态**，各态下表现是否不同？"编辑中（未保存）"的临时态与"确认 / 保存后"的表现是否**分开验证**、勿混为一条？ | 对象存在多个状态时适用；无状态的纯计算 / 纯展示不适用。**分工**：`状态迁移` 关注对象状态如何流转；"处理中点击取消"这类**反向操作**归 `逆向`；"保存后重开数据是否还在"归 `一致性`。示例：订单 待支付→已支付→已发货→已完成 / 已退款；配置项 未设置 / 默认 / 自定义 三态。 |
| `角色权限` | 不同角色 / 等级 / 登录态的**可见范围与操作边界**是否正确；以及能否**越界**访问不属于自己的数据 | 不同等级 / 登录与未登录 / 管理员与普通用户的差异是否生效？**越权**：修改 ID 能否访问他人数据（水平越权）？普通用户能否执行管理员操作（垂直越权）？跨租户是否隔离？ | 存在多角色 / 等级 / 私有数据时适用；全员一致且无私有数据则不适用。**分工**：合法身份下"能力是否有差异"为本轴正常面；"能否绕过授权越界访问"为本轴的**越权**追问（不单列一根轴，避免与本轴重复标注）。示例：普通用户修改 URL 中的订单 ID 打开他人订单详情。 |
| `来源入口` | 同一功能从不同入口 / 来源触发时表现是否一致 | 存在几个入口？从不同页面、外部链接、API 分别触发，行为是否一致？ | 功能有多个触发入口时适用；单一入口不适用。示例：从列表页、详情页、通知跳转三处发起同一操作，结果是否一致。 |

### C 组 · 并发与数据类（涉及写入、扣减，或数据存于多处时适用）

| 轴名（标签词） | 本轴考察什么 | 生成时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `幂等` | **同一操作重复执行**（连点 / 重试 / 重复消息）结果是否与执行一次相同 | 连续点击提交是否重复扣款 / 重复创建？超时重试是否执行两次？重复回调 / 重复消息如何处理？ | 凡有"提交 / 扣减 / 写入"即适用；纯读取 / 纯前端计算不适用。**分工**：`幂等` 为同一操作**重复多次**；`并发` 为多操作**同时**作用于同一资源。示例：连续点击三次提交，是否仅扣款一次、仅创建一笔订单。 |
| `并发` | 同一资源被**同时多次**操作时是否正确、无竞态 | 同一账号同时发起多个请求会怎样？限量 / 限流 / 计数在并发下是否准确？是否会超卖 / 超发？ | 存在共享资源 / 限量 / 计数时适用；无共享状态不适用。**分工**：与 `幂等` 的区别在"同时"与"重复"。示例：同一账号并发提交多笔下单，库存扣减与限流是否正确。 |
| `一致性` | 数据存于多处（主从库 / 缓存）或先写后读时，读到的是否正确且最新 | 写入后立即读取是否可读到（主从延迟）？缓存是否返回旧值？跨表 / 跨服务数据是否一致？**保存后退出重进 / 重新打开 / 重新登录，数据是否仍在且一致**（持久化验证，区别于编辑中的临时态——后者归 `状态迁移`）？ | 存在跨库读写 / 缓存 / 写后立即展示 / 需持久保存时适用；纯单点无持久化不适用。示例：提交订单后跳转"我的订单"新订单是否立即出现；设置项保存后退出重进是否保留。 |

### D 组 · 变更与非功能类（改动存量，或线上关键链路时适用）

| 轴名（标签词） | 本轴考察什么 | 生成时的展开追问 | 适用判断 + 与相邻轴分工 |
|---|---|---|---|
| `存量兼容` | 升级 / 加字段 / 改逻辑后，**老数据、老流程**是否仍正常、能否回滚 | 新增必填字段后老数据能否正常读取？逻辑变更后旧记录是否仍正确？可否回滚？数据迁移中断如何处理？ | 改动已有功能 / 数据结构时适用；全新独立功能不适用。**分工**：`存量兼容` 仅涉及**数据 / 版本 / schema** 的向后兼容，**不含运行环境兼容**（后者归 `环境兼容`）。示例：为订单表新增必填字段后，历史订单打开是否报错、能否回滚。 |
| `环境兼容` | 不同**运行环境 / 客户端 / 网络**下是否均正常 | 不同浏览器 / 分辨率？旧版本 App / 旧客户端是否仍可用？弱网 / 断网 / 超时如何表现？中断后能否重试或恢复？ | 存在多端 / 多客户端 / 明显网络依赖时适用；纯后端内部功能可不适用。**分工**：`环境兼容` 关注运行环境与网络（设备 / 浏览器 / 弱网）；`存量兼容` 关注数据 / 版本升级。二者常被混淆，须区分。示例：旧版本客户端打开新功能是否正常降级；弱网下请求超时后能否重试。 |
| `性能` | 高频 / 高峰 / 大数据量下的响应与容量边界 | 高峰并发下响应时间是否达标？大数据量下是否拖垮？排队时长是否可接受？ | 关键高频链路、有明确性能要求时适用；低频内部功能可不适用。示例：高峰期批量请求下的响应时长与成功率是否达标。 |
| `安全审计` | 敏感数据是否脱敏、敏感操作是否留痕可审计 | 手机号 / 支付信息展示是否脱敏？敏感操作是否有日志可查？数据落库是明文还是加密？ | 涉及个人信息 / 支付 / 敏感操作时适用；无敏感数据不适用。**分工**：`安全审计` 关注"应隐藏的是否隐藏、应留痕的是否留痕"；`可观测` 关注"出问题能否定位"。示例：操作记录中手机号是否脱敏、不落明文。 |
| `可观测` | 关键路径是否有日志 / 追踪 ID / 告警 / 监控，出问题能否定位 | 失败能否查到卡在哪一步？是否有追踪 ID 串联全链路？失败率是否有监控告警？ | 线上关键链路适用，越核心越应覆盖；纯静态展示可不适用。示例：请求失败能否定位失败环节、当日失败率是否有告警。 |

## 五、标签标注规则

- **一条测试点主要标注 1 个标签**（主标签）：优先取**最具体、信息量最高**的变化轴（如涉越权场景取 `角色权限`）；若该条属普通正常 / 临界 / 非法检查，则取路径类型词（`正向 / 边界 / 异常`）。
- **必要时至多再加 1 个补充标签**（具体场景词，如 `SSO超时`、`弱网`），便于人工扫视定位。**禁止单条测试点标注过多标签**，以免污染看板统计。
- 主标签优先取本清单词；确需表外词时，先参考同 Requirement / 同产品既有测试点的用词，尽量复用，以收敛同义词。

## 六、备注与边界

- **A/B/C/D 仅为分组，非必测顺序**：A 组高频适用（几乎每个功能均涉及输入），B/C/D 按功能特征启用。**A/B 轴**判明确不适用可静默；**C/D 八轴**默认存疑、除非 §二.1 正面证明不适用，不强套。
- **C、D 组最易遗漏，亦最易被"不适用"误判**：幂等 / 一致性 / 并发 / 存量 / 环境 / 性能 / 审计 / 可观测等技术面，正是需求文档通常不写的部分。**C/D 八轴默认存疑兜底**（见 §二.2）；仅 §二.1 形态门槛可证不适用者静默，不得默默略过。
- **标签非覆盖账本**：因标签为自由文本、清单仅软推荐（可能出现表外词、可能因判不适用而静默），**看板的"标签分布"仅为尽力而为的参考，非权威覆盖记录**。覆盖完整性以人工 review 测试点为准，而非统计标签数量。
