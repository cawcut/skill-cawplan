# 用例写作规范（A3 内容与拆合规则）

本文件是 Case 内容、字段语义和用例数量的唯一权威。四法只负责发现候选场景，见 `test-design-methods.md`；CSV 布局见 `csv-template-mapping.md`。

## 通用底线

- 具体文案、错误码、阈值、次数、长度、枚举和跳转只能来自测试点或五字段。源里逐字给出则原样带入 Title / Expected，不抽象、不意译、不挂诚实尾巴；源里没有则用方向描述和固定尾巴，不编硬值。
- 固定尾巴按源数据语言二选一：`(以实现为准)` / `(per implementation)`；`(具体文案以实现为准)` / `(exact copy per implementation)`；`(文案以实现为准)` / `(copy per implementation)`；`(上限/阈值以实现为准)` / `(limit/threshold per implementation)`。
- 用例内容语言跟测试点/五字段走；中英文、文字与数字之间留空格。
- `Tag / Group / TestPointTitle / TestPointId / RequirementId / moduleTreeNodeId` 原样继承，不改写、翻译或润色。`CaseId` 由脚本份内递增生成。

## Title

写成“触发条件 + 预期现象”，只表达一个核心验证场景。保留区分 Case 身份的关键动作、角色、入口、UI 原词和专有名词；把导航和中间过程下沉到 Steps。源给定的可核对值保持原文，禁用“正常、正确、系统正常处理”等模糊词。

判断源值是否必须保真：

1. 先看父测试点或五字段是否逐字给了具体句、错误码、状态码、枚举、数值阈值、单位或 UI 原词；引号只是信号，不是必要条件。
2. 若抽象后 SQA 无法按源逐字核对，该内容属于保真区，必须原样进入 Title；展开后的相关 Expected 同理。
3. 源只有“明确提示、应拦截”等方向描述时，才使用抽象描述和诚实尾巴。

最小校准：源写 `Please connect a Text input.` 时必须保留该句，不能改为“应提示必填输入缺失(具体文案以实现为准)”；源只写“给出明确提示”时不得反向编造提示句。

标题提炼只删过程，不删身份：同一弹窗的 `Cancel`、关闭 `X`、`Delete` 等关键动作必须保留；“打开菜单、弹窗内再次点击”等过程放 Steps。`TestPointTitle` 继承列始终保留原文。

## Preconditions 与 Steps

### Preconditions

只写 Case 开始前已经成立、且本 Case 不负责建立过程的外部既有条件，例如已有账号、权限、Feature Flag、基础环境或 fixture。多条写成 `1.\n2.`，无则写“无”或留空；仅标题态不填。

### Steps

写执行本 Case 时测试人员主动完成的操作，包括为验证目标添加节点、上传素材、建立连接、输入数据、切换选项和触发状态。不要因为它们是“准备工作”或过程较长就批量前移到 Preconditions；本次临时创建的数据也属于 Steps。

校准：

- ✅ Case 执行时添加节点、上传素材、建立连接并输入数据，逐项写入 Steps。
- ❌ 为缩短 Steps，把上述场景构造统一写进 Preconditions。

Step 用祈使语序和操作动词，写清对象及入口；验证、检查、确认等判断语义写入 Expected。

## Step / Expected 契约与粒度

- 每个保留的 Step 必须恰好对应一条非空 Expected；`steps.length === expected.length`，每个元素均非空。
- Expected 必须是明确可判定的测试信号，不限 UI；接口/请求响应、持久化数据、任务状态、生成物、事件、日志等均合法。
- 一个 Step 同时产生的多个关联信号可以写在同一条 Expected 中；一对一不等于一条 Expected 只能有一个信号。
- 不用“数据准备完成”等无实际观察价值的文字机械占位。若操作后没有独立测试信号，把它与后续操作合并到第一个有意义的检查点。
- 动作引发需要单独判定的页面、弹窗、列表、接口、数据或任务状态变化时，该动作必须独立成 Step；同页/同状态的连续铺垫若无中间检查价值可合并。

最小对照：

- ✅ 输入账号和密码后点击 Sign In → 登录失败并给出明确提示；❌ 分成“账号已输入”“密码已输入”等无观察价值的占位检查。
- ✅ 页面跳转、请求完成和最终数据落库是同一次连贯执行中的三个 Step/Expected，仍可属于一个 Case；❌ 仅因有三个 Expected 就拆成三个 Case。

## 多对象落实

TestPoint 合并描述 Audio/Video、多节点或多入口等对象时，Case 或 Steps 必须逐对象实际执行并分别配 Expected，不能继续写“或、均、各”概括。如果对象具有独立路径、处理或失败模式，按下节拆成独立 Case；只有同一失败模式且步骤能逐对象走完时才可合并。

校准：✅ 分别上传 Audio、Video 并逐项观察；❌ 写“上传 Audio 或 Video，均应被拦截”而未逐对象执行。

## 示例数据

优先给可直接执行的示例，尤其是累加、组合或凑边界的场景，但示例依赖的系统约束必须来自源：

- 源给出阈值时，可据此推导并标注示例输入，例如源写总限制 15s，可用 `(示例) V1=10s、V2=5s` 构造边界。
- 源未给阈值时，不得用示例偷渡约束；写“略超上限(上限以实现为准)”或转存疑。

## Priority

内部推 P0–P3，导出由脚本映射为 Critical/High/Medium/Low：主路/核心正向 P0；岔路、边界、主要非法输入 P1；异常流、次要非法、常见错误推测 P2；边缘错误推测 P3。涉金额、安全、高频或外部依赖升一级；低频、有降级方案或仅体验降一级，并限制在 P0–P3。历史缺陷多不自动升优先级，不设数量或比例门禁。

## 拆 / 合规则（用例数量的唯一裁决）

### 层 1：核心验证场景

核心验证场景是在一组起始条件、测试数据和执行路径下，围绕父测试点验证一个连贯行为结果。一个 Case 对应一个可独立执行的核心场景，但可包含多个顺序 Step 和对应 Expected。

判断顺序：先按层 2 识别离散/连续、EP、多对象和步骤形状，再判断这些检查点是否属于同一次连贯执行。

- 同一次执行中的连续动作和多个检查点合在一个 Case。
- 不同起始状态、输入分区、角色、入口、业务分支或最终失败模式，需要分别执行时拆 Case。
- 最终 Expected 字面相同不代表可以合并；不同起始条件、路径或失败模式仍分别执行。
- 多组数据只在“同一失败模式且仅换数据”并且 Steps 能把每个数据/对象逐一走完时合并；任一条件不满足则拆，无法判断则存疑。此合并条件不覆盖下文“离散选项与连续区间”的逐项规则。
- 信息不足不能成为无限拆分的理由；只保留有依据的最小充分场景。

每完成一个 Case，检查：它是否塞入了两套互不依赖的起始条件、数据或分支？若拆开后每条仍能独立执行并代表完整核心场景，则拆；若只是同一次执行中的多个检查点，则不拆。

校准：两条路径最终都显示“失败”，但起始条件、业务分支或失败模式不同，仍分别执行；不能仅因最终文案相同而合并。

### 层 2：EP

处理方式相同的有效等价类可合在一条 Case 中逐项执行；每个无效等价类单独一条。之后仍需通过层 1 判断。

### 层 2：离散选项与连续区间

先问“换值是否可能走不同处理/失败模式，中间值能否代表相邻值”：

| 类型 | 判定 | 当前规则 |
|---|---|---|
| 离散选项集 | 各项独立、无连续性，中间值不能代表相邻值，如语言、分辨率、固定档位 | 对源明确要求覆盖的每个值或类别逐项全测，各成一条 Case，Expected 写死源中的值；不得用“分别/各/与所选一致”合并 |
| 连续数值区间 | 同一逻辑处理不同量，失败集中在边界，中间值可代表相邻值 | 下限外、下限、上限、上限外分别形成边界场景；主路未覆盖时可加一个中间代表，不逐项穷举 |

数值外观不决定类型：固定 `5s/10s/15s` 下拉仍是离散选项；可任意输入的 `5–15s` 才是连续区间。源明确要求分别覆盖三类并为每类给出代表时，应按三类各成一条 Case；“如/例如”只说明代表，不据此把类别内所有成员继续扩成 Case。所有示例值仍受源值保真约束。

### 层 2：多对象与步骤

- 合并描述的对象必须按“多对象落实”实际执行；路径或失败模式独立则拆。
- 步骤拆分由“动作后是否存在需单独判定的测试信号”决定；Step 数量不决定 Case 数量。

## 完成检查

交付前只需确认：Title 通过源值保真；Preconditions/Steps 边界正确；Step/Expected 等长且逐项非空；源明确要求覆盖的离散值/类别没有被概括合并；Case 拆合符合层 1 与层 2；继承列原样，其中 `TestPointTitle` 保持父测试点标题、不得替换成 ID；没有数量/比例门禁、设计方法列或无依据的具体值。发现无法从源判断的内容时写方向占位或进入存疑，不按“合理假设”补齐。
